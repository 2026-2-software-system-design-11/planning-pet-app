# 저장 방식 측정 (2026-11-14)

[D-08](../decisions.md)의 근거다.

질문: 일정이 몇 년 동안 수만 개 쌓이면 통계, 체크 하나 저장, 자동 배치, 저장 중 꺼짐에 DB가 필요한가.

## 측정 방법

- 한 번 쓰고 버리는 측정 코드(Java 한 파일)로 쟀다. 드라이버는 sqlite-jdbc 3.54.1.0, h2 2.5.252(Maven Central). 측정 코드는 이 저장소에 넣지 않았다.
- 데이터: 2020-01-01부터 하루 10개(고정 수업 2개, 옮길 수 있는 할 일 8개). "오늘"은 전체 기간의 80% 지점.
- 방식:
  - file: 전부 메모리에 두고, 바뀔 때마다 파일 전체를 임시 파일에 쓰고 fsync한 뒤 교체한다.
  - sqlite: 기본 설정(rollback journal, synchronous FULL).
  - sqlite-wal: WAL, synchronous NORMAL. 커밋마다 fsync하지 않는다.
  - h2: 기본 설정.
- 체크 하나 저장: 할 일 완료 상태와 누적 보상을 같이 바꾸고 디스크에 쓴다. DB는 트랜잭션 하나로 묶는다.
- 자동 배치: 14일 범위를 읽고, 고정 일정을 피해 09:00부터 23:00까지 빈 칸에 할 일을 앞에서부터 채우고, 결과를 저장한다(실제 알고리즘이 아니라 비용을 보려는 흉내).
- 같은 JVM 안의 시간은 중앙값이다.
- "첫 열기"는 새 JVM에서 `main`이 시작된 뒤부터 메인 화면에 필요한 데이터가 준비될 때까지다(3번 중 가운데). 파일은 전체를 읽어 메모리에 올리고 누적 보상을 검산한다. DB는 연결(드라이버 로딩 포함)하고 오늘 할 일과 누적 보상만 읽는다. JVM 자체 시작(빈 프로그램 약 20ms)과 Swing 창 만들기는 넣지 않았다.
- 처음에는 닫기까지 재서 h2가 크게 나왔다. h2는 닫을 때 100~260ms를 더 쓴다. 아래 표는 열기만 다시 잰 값이다.
- 환경: 이 맥 한 대(SSD), JDK 21.0.11.

## 읽는 법

- 첫 열기 말고는 10만 개에서도 사람이 지연을 느끼는 100ms 아래다. 첫 열기는 앱을 켤 때 한 번이다. 파일은 데이터 양에 비례해 늘고(2만 61ms, 10만 156ms), sqlite는 양과 관계없이 약 0.3초(네이티브 라이브러리를 꺼내는 비용으로 보임, 확인 안 함), h2는 약 0.12초로 일정했다.
- 체크 하나 저장은 DB가 수십 배 빠르지만, 파일도 10만 개에서 24ms다.
- 저장 중 꺼짐은 "임시 파일에 쓰고 교체"만 지키면 파일도 DB와 같은 결과다. 제자리 덮어쓰기는 실제로 깨졌다.
- 통계에서 h2가 빠른 것은 같은 질의 결과를 캐시했기 때문일 수 있다(확인 안 함).

## 확인하지 않은 것

- 전원이 나가거나 운영체제가 멈추는 경우. `kill -9`는 프로세스만 죽인다. macOS의 fsync는 디스크 캐시까지 비우지 않으므로(F_FULLFSYNC 아님) 파일과 sqlite 기본 설정 모두 같은 조건이다.
- Windows와 HDD에서의 시간.
- 실제 자동 배치 알고리즘의 계산 시간. 여기서는 저장 방식에 따른 조회와 저장 비용만 봤다.

## 배포 크기

- sqlite-jdbc jar 12.1MB(여러 운영체제용 네이티브 라이브러리 포함), h2 jar 2.7MB, 파일 방식 0MB.
