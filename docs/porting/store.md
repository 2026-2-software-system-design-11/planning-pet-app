# 단위 M8. 저장

[본 구현으로 옮기기](../porting.md) 1절 표의 단위 M8이다. 07의 `DataStore`, `SqliteDataStore`, `Schema`, `AppController.change`, `AppData.copy`, `restore`를 옮긴다. 기준은 06 21번, 22번과 그 검사 줄, 07 저장 형식, D-08, D-111이다. 프로토타입은 저장이 없어 비교 기준이 없고 06 검사 줄만 기준이다(porting.md 2절 6번).

PR 하나의 크기 한도(1절) 때문에 넷으로 나눠 옮긴다. 되돌리기(`AppData.copy`, `restore`, `TaskBook`의 지운 보상 기록 생성자, 값 넣는 메서드)는 #351, 저장의 틀(`DataStore`, `LoadResult`, `AppController.change`)은 #354, sqlite 파일 저장과 읽기(`Schema`, `SqliteDataStore`)는 #352, 형식 번호와 강제 종료(07의 형식 번호와 변환, T-STORE-3, 4, 6, 7)는 #353이다. 시작할 때 읽고 `UNREADABLE`이면 창을 띄우는 `Main` 잇기는 창이 필요해 S1 창 틀 단위가 한다.

07 안에서 정한 것과 그 까닭:

- **되돌려도 일정과 펫은 같은 객체다.** `restore`는 사본의 값을 지금 있는 같은 `id`의 일정, 같은 종류의 펫 객체에 넣는다. 변경으로 생긴 일정과 펫은 빠지고, 변경이 지운 일정은 그 객체가 목록에 돌아온다. 일정 입력 창은 저장에 실패하면 열린 채 남고(06 22번, T-SAVE-3) 다시 저장할 때 잡아 둔 `Task`를 넘긴다. 사본 객체로 바꿔 넣으면 창이 잡은 일정이 목록 밖에 남아 다시 저장해도 바뀌지 않는다. 일정의 값을 넣는 `Task.copy`, `setFrom`은 `TaskBook`만 부르도록 package-private이다(D-109). `copy`는 새 `AppData`에 `restore`한 것이라 같은 시계를 쓰고, 데이터 변경 알림을 받는 곳은 옮기지 않는다.
- **지운 보상 기록은 `TaskBook` 생성자 인자로 넣는다.** 07이 M8에 맡긴 길이다(07 "06에 없는 메서드"). 저장의 읽기가 `task` 표의 `deleted` 열로 나눈 일정을 `AppData` 생성자로 넘기고 `AppData`가 `TaskBook`에 넘긴다. 바꾸는 메서드보다 길이 좁다. 읽은 기록의 순서는 넣은 순(`seq`)이다. 표에 지운 순서 열이 없다(07 저장 형식).
- **읽기에 쓰는 값 넣는 메서드.** 06 데이터 절의 값마다 `AppData`와 `PetState`에 값 하나를 넣는 메서드를 둔다(07 읽는 법이 그리지 않는 메서드). 저장의 읽기(#352)가 쓰고, 이 단위의 검사가 모든 값을 채운 데이터를 만든다. 보상, 상점 같은 규칙은 그 규칙을 옮기는 단위가 이 메서드를 부르는 규칙 메서드로 더한다.
- **`LoadResult`는 상태, 읽은 데이터, 이유를 담는 record다.** 상태는 `LOADED`, `FIRST_RUN`, `UNREADABLE`, 이유는 값 목록(`NEWER_VERSION` 새 버전에서 만든 파일, `NOT_DATA_FILE` 플래닝펫 데이터 파일이 아님, `UPGRADE_FAILED` 옮기기 실패, `READ_ERROR` 읽기 오류)이다. 06은 "이유와 함께"라고만 적었고 05는 새 버전의 글만 정했다. 화면 글은 그 창을 옮기는 S1이 05와 함께 정한다.
- **`change`의 `errors`는 창 내용만 받는다.** "{what} 저장에 실패해서 바꾸기 전으로 돌렸어요."를 넘기고 창 제목 "저장하지 못했어요"는 창을 띄우는 view가 붙인다(07 "controller는 창을 모른다").
- **`edit`가 예외를 던지면 되돌리고 다시 던진다.** 06에 없는 길이다. 복사본으로 되돌리고, 저장하지 않고, 데이터 변경 알림을 한 번 보낸 뒤 같은 예외를 던진다. 되돌리지 않으면 반쯤 바뀐 값이 남아 틀린 값이 저장된다. `AppControllerTest.editThrowsRestoresAndRethrows`가 확인한다.
- **표와 앱 데이터 사이는 `app.store`의 `Rows`가 바꾼다.** `AppData`를 표마다 기본 키에서 행으로 가는 모음으로 바꾸고, 읽은 행으로 `AppData`를 만든다. `save`는 지난 저장(`saved`, 07)을 같은 모음으로 바꿔 견주고, 없어진 행을 지우고 달라진 행을 지운 뒤 다시 넣는다. `app` 표는 기본 키가 없는 한 행이다. 검사가 바뀐 행만 쓰는지 보도록 지난 `save`가 쓰고 지운 행 수를 package-private으로 읽는다.
- **첫 `save`는 표를 만들고 형식 번호를 적는 일까지 데이터와 같은 트랜잭션 하나로 한다.** 첫 저장 도중 꺼지면 sqlite가 되돌려 표 없는 빈 파일이 남고, #353이 그 파일을 첫 실행으로 읽는다.
- **형식 번호 0 파일은 표가 없으면 첫 실행, 표가 있으면 `NOT_DATA_FILE`이다.** 플래닝펫이 표를 만들면 같은 트랜잭션에서 번호 1을 적으므로, 번호 0에 표가 없는 파일은 첫 저장 도중 꺼진 빈 파일이고 번호 0에 표가 있는 파일은 다른 프로그램의 sqlite 파일이다. 빈 파일은 첫 `save`가 표를 만든다.
- **옮기는 단계는 `Schema.STEPS` 목록이다.** `STEPS.get(n - 1)`이 형식 n 파일을 n + 1로 옮기고 `VERSION`은 단계 수 + 1이다. 형식이 1뿐이라 목록이 비어, 06 T-STORE-7이 적은 "형식 2가 생기면 1 파일로 검사한다"를 지금은 그대로 할 수 없다. 사본과 옮기기 코드는 지금 두고, 검사는 단계 목록을 package-private 생성자로 바꿔 끼워 검사만 쓰는 형식 2(`app` 표에 처음 값이 있는 열 하나를 더한다)로 1 파일을 옮긴다. 형식 2를 기다리면 그때 처음 도는 사본과 실패 되돌리기 코드가 검사 없이 들어가기 때문이다. 형식 2가 생기면 그 단계로 같은 검사를 하고 06의 새 값 채우기를 그 값으로 본다.
- **T-STORE-6은 `SaveKillTest`가 새 JVM으로 저장을 되풀이하다 SIGKILL로 끈다(07 실행 모드).** 창은 열지 않는다(`java.awt.headless=true`). 세대마다 포인트와 할 일 2만 개의 제목을 모두 바꿔 저장 하나가 길게(이 컴퓨터에서 약 100ms) 걸리게 하고, 첫 저장을 마친 뒤 0ms에서 285ms까지 회차마다 늦춰 끈다. 읽은 값이 한 세대로 온전하고 마친 세대이거나 그다음인지 본다. 재 보니 20번 가운데 14번이 저널이 남은 채 꺼져 읽기 전용 열기가 실패한 뒤 다시 여는 길을 지났다. 테스트는 약 23초 걸린다.
- **`sample` 표의 행은 `sampleIds`마다 하나다.** `sampleLooks`의 값은 같은 행의 열이다. 31번은 둘을 함께 채우고 함께 비운다.
- **`load`는 먼저 읽기 전용으로 연다(07).** 파일이 없으면 `FIRST_RUN`이다. sqlite 파일이 아니면 `NOT_DATA_FILE`, 형식 번호가 `Schema.VERSION`보다 크면 `NEWER_VERSION`이고 파일을 건드리지 않는다. 그 밖의 읽기 실패는 `READ_ERROR`다. 저장 도중 꺼져 저널이 남은 파일은 읽기 전용으로 열면 sqlite가 되돌리지 못하고 `SQLITE_READONLY_ROLLBACK` 오류를 낸다(sqlite-jdbc 3.54.1.0으로 확인). 그때만 읽고 쓰기로 다시 열어 sqlite가 바꾸기 전으로 되돌린 뒤 읽는다(06 21번 "커밋 전에 꺼지면 sqlite가 다음에 열 때 바꾸기 전으로 되돌린다", T-STORE-6). 그 파일은 sqlite 파일이라 T-STORE-3의 "건드리지 않는다"에 들지 않는다.

## 1. 화면에서 따라 할 단계

이 단위는 화면이 없다. 되돌리기와 저장, 읽기가 화면에 드러나는 곳은 아래이고, 화면은 S1~S10 단위가 옮긴다.

1. 저장할 수 없을 때(디스크가 찼을 때) 할 일 체크박스를 누르면 "저장하지 못했어요" 창에 "할 일 완료 저장에 실패해서 바꾸기 전으로 돌렸어요."가 보이고 체크와 포인트가 누르기 전으로 돌아간다(05 메인 입력 항목 4, T-SAVE-1).
2. 같은 때 일정 입력 창에서 "저장"을 누르면 창이 닫히지 않고 입력값이 남은 채 저장 실패 창이 뜬다. 디스크를 비우고 다시 "저장"을 누르면 저장된다(05 일정 입력 창 입력 항목 9, T-SAVE-3).
3. 나의 방에서 쿠션을 사다가 저장에 실패하면 포인트, 보유 목록, 놓인 아이템이 되돌아간다(05 나의 방 입력 항목 12, T-SAVE-2).
4. 메인에서 할 일 체크박스를 누르고 앱을 끈 뒤 다시 켜면 체크, 보유 포인트, 펫 카드의 레벨 막대가 그대로다(06 21번, T-STORE-1).
5. 빈 폴더로 앱을 열면 반려동물 고르기 창이 뜨고, 고르기 전에 끄면 폴더에 파일이 생기지 않는다(UC-01 2a, T-STORE-2).
6. 새 버전의 플래닝펫이 만든 `planningpet.db`나 플래닝펫 데이터가 아닌 `planningpet.db`가 있는 폴더로 앱을 열면 파일 위치와 원인(새 버전이면 "새 버전의 플래닝펫에서 만든 파일이에요")이 적힌 오류 창이 뜨고 앱이 끝난다. 파일은 그대로다(05 오류 처리, UC-01 2b, T-STORE-3, 4). 창은 S1이 옮긴다.

## 2. 입력의 경계와 결과

프로토타입 결과는 모두 "없음"이다(저장이 없다). 06에 검사 줄이 없는 되돌리기와 `change`의 경계는 `E-BOOK`, `E-PET`(M7에 이어서), `E-APP`(M7에 이어서), `E-SAVE`, `E-STORE` 번호다. "모든 값을 채운 데이터"는 06 데이터 절의 값마다 처음 값과 다른 값을 넣은 앱 데이터다. 일정은 끝내고 보상을 받은 기간 할 일, 반복 사본, 다음 날 새벽 시각의 고정 일정이 있고, 지운 보상 기록 하나, 장신구 둘을 입은 펫 둘이 있다.
