# 단위 M6. 일정 고치기와 지우기

[본 구현으로 옮기기](../porting.md) 1절 표의 단위 M6이다. 07의 `TaskBook.update`, `clearTime`, `delete`와 지운 일의 보상 기록 `deletedRewarded`를 `planningpet.schedule.model`에 옮긴다. 기준은 06 4번(끌어 놓기 빼고), 5번과 그 검사 줄, 프로토타입 `schedule/model/TaskBook`의 고치기와 지우기 부분이다. PR 하나의 크기 한도(1절) 때문에 수정 창 저장(`update`의 수정 창 길)은 #339, 시각 고치기 창(`update`의 시각 고치기 창 길, `clearTime`, D-98의 "밤 4시")은 #340, 지우기(`delete`, `deletedRewarded`)는 #341로 나눠 옮긴다. 끌어 놓기(`placeAt`)는 C2, 수정 창과 범위 물음 창은 S4 일정 입력 창 단위다. T-EDIT-1의 보유 포인트는 `AppData`의 값이라 M7, M9가 확인한다.

07 안에서 정한 것과 그 까닭:

- **범위는 값 목록 `EditScope`이고 값은 `ONLY_THIS`, `THIS_AND_AFTER`다.** 07은 타입으로만 적었고 06 4번의 이름대로다. 프로토타입은 `boolean thisAndAfter`였다.
- **`Task`의 값은 같은 패키지에서만 바꾸는 메서드로 바꾼다.** D-109대로 public 필드로 열지 않는다. 값 하나만 바꾸는 메서드(`setTitle` 같은 것)는 07이 그리지 않는 메서드이고, `TaskBook` 밖의 층이 일정을 바꾸지 못하게 package-private으로 둔다. 시작 시각은 `nextDay`와 함께 하나의 값(06 4번 "시작 시각(`nextDay` 포함)")이라 한 메서드로 바꾼다.
- **`update`는 넘어온 값을 다시 검사하지 않는다.** 06 4번의 입력은 "검사를 통과한 새 값"이고 오류는 종류가 다를 때 하나다(E-EDIT-12).

## 1. 화면에서 따라 할 단계

이 단위는 화면이 없다. 수정 창 저장이 화면에 드러나는 곳은 아래이고, 화면은 S4 일정 입력 창 단위가 옮긴다.

1. 끝낸 "논문 읽기"의 연필 "수정"을 눌러 "일정 수정" 창에서 날짜 2026-11-20, 시작 20:00, 120분으로 "저장"을 누르면 17일 목록에서 빠지고 20일로 옮겨 가며, 끝냄과 받은 보상은 그대로다([UF-10-3](../user-flows.md) 2단계, T-EDIT-1).
2. 반복 일정 "병원 실습"을 고쳐 저장하면 "'병원 실습'은 반복 일정이에요. 어디까지 바꿀까요?"를 묻고, "이 일정만"은 그 하나, "이후 반복 모두"는 그 날짜부터 뒤 사본이 바뀐다([UF-6-2](../user-flows.md) 3, 4단계, T-EDIT-2, T-EDIT-7).

## 2. 입력의 경계와 프로토타입 결과

프로토타입 결과는 `prototype/src`를 컴파일한 클래스로 `TaskBook.update(task, draft, thisAndAfter)`를 부르는 버리는 Java 파일에서 얻었다(develop `ad75ee7`, JDK 21.0.11). 따로 적지 않으면 오늘은 11-18(수)이고 일정은 할 일, 30분, 메모 빈 글, 유형 기타다. 넣는 값은 그 일정의 수정 창을 열었을 때의 값(기간 할 일은 날짜 칸이 기간 첫날이고 시작 칸이 꺼져 있다)에서 적은 칸만 바꾼 것이다. 경계마다 본 것:

- E-EDIT-4, 5: 수정 창은 반복 사본이면 기간 안에 하기가 꺼져 있고(D-65), 기간을 켜면 시작 시각 칸을 끈다(D-68). 다른 길로 들어와도 반복 사본은 기간 할 일이 되지 않고, 기간 할 일은 시각 없이 된다.

- E-EDIT-12: 저장 전 검사는 controller가 한다(seq-uc05의 `validate()`). `add`는 검사를 통과하지 않으면 `IllegalArgumentException`이지만(E-ADD-1) 06 4번은 그 오류를 적지 않았다.
