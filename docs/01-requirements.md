# 01. 개요와 요구사항

근거 자료: 팀 기획 노트(2026-11-14 사진), CP1 보고서(2026-11-03), 배포 목표(많은 사람이 설치해 써 보게 한다), 팀이 준 시각 예시(2026-11-23, 나의 방, 캐릭터 창, 통계).

## 1. 대상 앱

플래닝펫은 일정 관리와 반려동물 키우기를 합친 Java Swing 데스크톱 앱이다.
사용자가 할 일을 해내면 포인트와 경험치를 얻고, 그것으로 반려동물(고양이 한 마리, 강아지 한 마리까지)을 키우고 방을 꾸민다(D-48).

이번 버전은 데스크톱 앱 하나다. 오늘 할 일만 보여 주는 폰 앱과 계정, 동기화는 다음 단계다(D-14).

## 2. 특징과 기존 앱 비교

| 앱 | 하는 일 | 플래닝펫과 다른 점 |
|---|---|---|
| Google 캘린더 | 일정 기록과 알림 | 해낸 일에 대한 보상이 없다 |
| Habitica | 할 일을 RPG 퀘스트로 바꾼다 | 전투와 파티 중심이라 익힐 것이 많다 |
| Forest | 집중하는 동안 나무가 자란다 | 일정 관리 기능이 없다 |
| Finch | 자기관리 목표를 하면 펫이 자란다 | 모바일 앱이고 날짜와 시간이 있는 일정 관리가 중심이 아니다 |

플래닝펫만의 특징:

- **그날의 브리핑**: 그날 처음 창을 열면 펫이 오늘 할 일을 알려 준다(D-14).
- **일정과 성장의 연결**: 할 일을 체크하면 홈 펫 카드의 "오늘 끝낸 일" 막대가 차고 펫의 레벨이 오른다. 레벨이 오르면 펫에게 입힐 장신구가 열린다(D-51).
- **데스크톱, 오프라인**: 공부하고 과제하는 노트북에서 계정 없이 바로 쓴다.

## 3. 이해관계자

| 이해관계자 | 원하는 것 |
|---|---|
| 사용자 (20대 대학생, 취준생) | 해야 할 일을 놓치지 않고, 해낸 만큼 보상받고 싶다 |
| 배포로 만날 일반 사용자 | 설치가 쉽고, 업데이트해도 데이터가 남아 있기를 바란다 |
| 팀 (3명) | 역할(Model, View, Controller)대로 나눠 만들 수 있고 학기 안에 끝나는 범위 |
| 교수 | 수업 내용(요구사항, 유스케이스, UML, Swing MVC)을 적용한 설계 |

## 4. 사용 장면

장면과 시간대는 조사 문서의 사용자 여정 추정을 따른다([research/design.md](research/design.md) 6절, D-14).

- **S-1 개강 첫 주**: 노트북에 플래닝펫을 설치하고 반려동물을 고른다. 이번 학기 수업을 일정관리 시간표에 넣는다.
- **S-2 수업 중**: 필기하려고 켜 둔 노트북에서, 오후 3시에 하기로 한 과제를 10분 전에 알려 준다. 창을 닫아 두었어도 트레이에 있던 앱이 알린다.
- **S-3 저녁 공부**: 도서관에서 노트북을 열면 그날 처음 보는 창이라 고양이가 오늘 남은 할 일과 마감이 가까운 과제를 알려 준다. 출석 보상 +20P를 받는다. 과제를 하나 끝내 체크할 때마다 포인트를 받고 고양이 옆 "오늘 끝낸 일" 막대가 한 칸 찬다. 몇 시간 동안 창을 켜 둔 채 공부한다.
- **S-4 주말**: 다음 주에 할 일을 넣고 자동 배치로 빈 시간에 놓는다. 모은 포인트로 나의 방 상점 칸에서 쿠션을 미리보기로 놓아 보고 산다. 통계에서 이번 주에 해낸 만큼을 본다.
- **S-5 시험 기간**: 하루 할 일이 열 개를 넘고 마감이 몰린다. 메인 목록과 시간표에서 무엇부터 할지 본다.
- **S-6 방학 뒤**: 몇 주 만에 앱을 연다. 고양이가 반겨 주고, 지난 일로 혼내지 않는다.

S-3의 브리핑과 막대는 기획 노트에 있다. 노트의 브리핑은 아침에 컴퓨터를 켤 때였지만, 학교생활 앱을 아침에 여는 사람이 적다는 추정에 따라 그날 처음 창을 열 때로 바꿨다. 통계 화면은 처음에 이번 버전에서 빼서(D-05) 장면에 없었고, D-55로 이번 버전에 넣으며 S-4에 더했다.

## 6. 미정

기획 노트와 CP1만으로는 정할 수 없거나, 서로 맞지 않는 것들이다. 정해진 것은 [decisions.md](decisions.md)로 옮긴다.

- **Q-01 URL 파싱 (다음 단계).** 이번 버전에서는 만들지 않는다(D-26). 다음 단계에서 목적부터 정한다. 사용자가 어떤 상황에서 URL을 넣는지(과제 공지, 채용 공고, 공모전 등), 그 목적에 URL 파싱이 가장 나은 방법인지 다른 방법(글 붙여넣기, 파일 가져오기, 캘린더 구독 등)과 비교한다. 그 뒤에 읽는 방식(페이지 구조 읽기, LLM)과 API 키 관리를 정한다. 학교 LMS처럼 로그인해야 보이는 페이지는 주소만으로 읽을 수 없다는 점도 비교에 넣는다.
- **Q-15 기존 앱 비교의 근거.** 2절의 비교는 각 앱의 널리 알려진 특징으로 썼고, 최신 기능은 확인하지 않았다.

Q-03, Q-04, Q-05, Q-06, Q-08, Q-09, Q-10, Q-12, Q-13, Q-14, Q-16은 D-15부터 D-29로 풀었다.
