# 06. 함수 명세

유스케이스([02-usecases.md](02-usecases.md))와 결정([decisions.md](decisions.md))을 코드의 함수로 옮긴다. 형식은 개인과제 CP3 양식의 FUNCTION SPECIFICATION(시그니처, 입력, 출력, 하는 일)에 쓰는 곳, 오류, 검사 표를 더했다.

## 읽는 법

- 검사 표의 한 줄은 JUnit 테스트 하나다. 테스트 이름에 검사 번호(예: `T-DAY-1`)를 넣는다. 만든 앱이 이 표를 모두 통과하면 이 명세대로 만든 것이다.
- 지금 시각은 주입한 `java.time.Clock`에서 얻는다. 표의 시각은 운영체제 시간대의 시각이다.
- 표의 날짜는 2026년이다. 2026-11-16은 월요일이다.
- "오늘"은 앱 날짜(D-15)다. 포인트는 P, 경험치는 "경험치 N"으로 적는다.
- 패키지는 도메인별로 나누고, 도메인 안을 `model`, `view`, `controller`로 나눈다(D-46). 예: `planningpet.schedule.model`. 클래스 사이의 관계와 저장 파일 형식은 07에서 그린다.
  - `model`은 데이터와 규칙이다. Swing과 AWT를 쓰지 않는다.
  - `view`는 Swing 화면이다. model을 읽어 그리고, 바꿀 때는 controller를 부른다. 다른 도메인의 controller도 부를 수 있다.
  - `controller`는 view의 동작을 받아 model을 바꾼다. 바꾸는 일은 22번 `AppController.change`로 감싸서, 저장과 데이터 변경 알림이 변경 하나에 한 번씩 나가게 한다.
  - 펫 말만 바꾸는 동작(달력 날짜 고르기, 그날 두 번째부터 창이 보일 때)은 저장할 데이터(아래 "데이터" 표)를 바꾸지 않으므로 22번을 거치지 않고 알림만 보낸다.
  - 화면 전환이나 주 옮기기처럼 model을 바꾸지 않는 다시 그리기는 데이터 변경 알림을 쓰지 않고 view끼리 한다.
  - 진입점(`main`이 있는 클래스)은 세 패키지에 넣지 않고 `planningpet.app`에 둔다.

| 도메인 | 패키지 | 이 문서의 함수 |
|---|---|---|
| 일정 | `planningpet.schedule` | 2~7번(`TaskDraft`, `TaskBook`), 14번(`DefaultDates`), 17번(`Reminders`), 18번(`AutoPlacer`), 19번(`TimetableLayout`), 26번(`CalendarCell`) |
| 보상 | `planningpet.reward` | 8~11번(`Rewards`, `Level`), 13번(`DailyProgress`, 성취도 막대는 게임 요소다. D-04, D-22) |
| 펫 | `planningpet.pet` | 16번(`PetTalk`, 글자 규칙은 공통), 20번의 놓기(`Room`), 27번(`Bond`), 28번과 30번(`PetController`, 장신구 표 `Wardrobe`, 자세 `Poses`) |
| 상점 | `planningpet.shop` | 20번의 사기, 만족도, 찾기(`Shop`) |
| 통계 | `planningpet.stats` | 29번(`Stats`) |
| 홈 | `planningpet.home` | 메인 화면과 그 달력에서 날짜 고르기(UC-09). 여러 도메인을 모아 보인다 |
| 설정 | `planningpet.settings` | 설정 화면 |
| 앱 | `planningpet.app` | 12번(`Visits`, 15번만 부른다), 15번과 22번(`AppController`), 21번(`DataStore`), 23번(`DayWatcher`), 24번(`SingleInstance`), 25번. 진입점, 창 틀, 앱 데이터 |
| 공통 | `planningpet.common` | 1번(`AppDay`), 16번의 글자 규칙(받침, 조사, 제목 줄임. 여러 도메인이 쓴다). 디자인 시스템의 색과 부품 |

## 1. `LocalDate AppDay.of(LocalDateTime time)`

시각이 속한 앱 날짜를 돌려준다.

- **쓰는 곳**: "오늘"이 필요한 모든 곳(UC-01, UC-02, UC-07, UC-09, UC-13)
- **입력**: 시각
- **출력**: 앱 날짜

## 2. `List<FieldError> TaskDraft.validate()`

일정 입력 창에 쓴 값이 저장할 수 있는 값인지 본다.

- **쓰는 곳**: 일정 입력 창의 저장(UC-03, UC-05), 빠른 추가(UC-04)
- **입력**: `TaskDraft`(종류, 제목, 유형, 날짜, 시작 시각, 걸리는 시간, 메모, 반복 끝 날짜). 반복을 고르지 않았으면 반복 끝 날짜는 `null`이다. 유형은 목록에서만 고르므로 검사하지 않는다(D-54).
- **출력**: 잘못된 칸과 문장의 목록. 칸 순서(제목, 시작 시각, 걸리는 시간, 메모, 반복)로 담는다. 비어 있으면 저장할 수 있다. 수정(4번)일 때는 반복 칸을 검사하지 않는다(D-42).
- **하는 일**: 제목은 앞뒤 공백을 지운 뒤 잰다. 날짜는 제한이 없다(지난 날짜도 된다). 아래 표 밖의 값은 모두 통과한다.

|---|---|---|
| T-VAL-1 | 제목 "  과제  ", 할 일, 30분 | 오류 없음. 저장되는 제목은 "과제" |

| T-VAL-5 | 고정 일정, 시작 시각 없음 | 시작 시각: "고정 일정은 시작 시각이 있어야 해요" |
| T-VAL-6 | 시작 09:03 | 시작 시각: "5분 단위로 정해 주세요" |
| T-VAL-7 | 시작 23:30, 30분 | 오류 없음(끝 24:00) |
| T-VAL-8 | 시작 23:30, 40분 | 시작 시각: "하루 안에 끝나야 해요" |
| T-VAL-9 | 걸리는 시간 0, 27, 730 | 각각 걸리는 시간: "10분부터 720분까지, 5분 단위예요". 10, 75, 720은 오류 없음 |

## 3. `List<Task> TaskBook.add(TaskDraft draft)`

검사를 통과한 입력으로 일정을 만든다.

- **쓰는 곳**: UC-03, UC-04
- **입력**: `validate()`가 오류 없음을 돌려준 `TaskDraft`
- **출력**: 만든 일정. 반복이면 사본 전부를 날짜 순으로 돌려준다.
- **오류**: 검사를 통과하지 않은 입력이면 `IllegalArgumentException`
- **하는 일**: 새 일정은 `done` false, 보상 0이고 유형은 입력값이다(빠른 추가는 기타, D-54). 반복이면 시작 날짜부터 끝 날짜까지 7일씩 더한 날마다 사본을 만들고 같은 `seriesId`를 준다(D-17). `seq`는 날짜 순으로 하나씩 준다.

| 검사 | 처음 상태 | 하는 것 | 결과 |
|---|---|---|---|
| T-ADD-1 | 일정 없음, `nextSeq` 1 | 할 일 "과제" 11-16 추가 | 일정 1개, `seq` 1, `done` false, 보상 0, `seriesId` null. `nextSeq` 2 |
| T-ADD-2 | T-ADD-1 뒤 | 할 일 하나 더 추가 | 새 일정의 `seq` 2 |
| T-ADD-3 | 일정 없음 | 고정 일정 11-16(월) 10:30, 75분, 반복 끝 12-28 | 7개(11-16, 11-23, 11-30, 12-07, 12-14, 12-21, 12-28). 모두 같은 `seriesId`, `seq` 1~7 |
| T-ADD-4 | 일정 없음 | T-ADD-3과 같고 반복 끝 12-30(수) | T-ADD-3과 같은 7개 |

## 4. `void TaskBook.update(Task task, TaskDraft draft, EditScope scope)`

이미 있는 일정을 고친다.

- **쓰는 곳**: UC-05
- **입력**: 고칠 일정, 검사를 통과한 새 값, 범위(`ONLY_THIS` 또는 `THIS_AND_AFTER`). 수정 창에는 종류와 반복 칸이 비활성이라 바뀌지 않는다. 반복 사본이 아니면 화면은 범위를 묻지 않고 `ONLY_THIS`를 넘긴다(D-42).
- **오류**: 종류가 다르면 `IllegalArgumentException`
- **하는 일**: 제목, 유형, 날짜, 시작 시각, 걸리는 시간, 메모만 바꾼다(유형은 D-54의 입력 창 칸). `id`, `seq`, `seriesId`, `done`, 보상은 그대로 둔다(D-18). `ONLY_THIS`는 고친 하나만 바꾼다. `THIS_AND_AFTER`는 같은 `seriesId`에서 날짜가 고친 사본의 원래 날짜와 같거나 뒤인 사본 모두에 제목, 유형, 시작 시각, 걸리는 시간, 메모를 넣고, 날짜는 고친 사본 하나만 바꾼다(D-42, D-54). 시각 고치기 창(D-32)에서 부르면 시작 시각과 걸리는 시간만 넣는다.

| 검사 | 처음 상태 | 하는 것 | 결과 |
|---|---|---|---|
| T-EDIT-1 | 끝낸 할 일, 보상 10P와 경험치 10, `rewardDay` 11-16 | 날짜를 11-20, 걸리는 시간을 120분으로 | 날짜와 시간만 바뀐다. `done`, 보상, `rewardDay`, 보유 포인트 그대로 |
| T-EDIT-2 | T-ADD-3의 사본 7개 | 11-30 사본의 시작을 13:00으로, `ONLY_THIS` | 그 하나만 13:00. `seriesId` 그대로 |
| T-EDIT-3 | `seq` 3인 할 일 | 제목을 고침 | `seq` 3 그대로 |
| T-EDIT-4 | 시각 없는 할 일, 30분 | 시작 14:00, 60분으로(시각 고치기 창, D-32) | 시작 14:00, 60분. 6번 `dayPlan`의 `timed`로 옮겨 간다 |
| T-EDIT-5 | 같은 날 시각 없는 할 일 seq 1, seq 5와 시작 10:00인 할 일 seq 3 | seq 3의 시작 시각을 빼기 | seq 3은 시작 시각 없음. `dayPlan`의 `untimed`는 seq 1, 3, 5 순이다 |
| T-EDIT-6 | 고정 일정 | 시작 시각을 빼기 | 2번 검사 "고정 일정은 시작 시각이 있어야 해요"로 바뀌지 않는다 |
| T-EDIT-7 | T-ADD-3의 사본 7개 | 11-30 사본의 시작을 13:00으로, `THIS_AND_AFTER` | 11-30부터 12-28까지 다섯 개가 13:00. 11-16, 11-23은 10:30 그대로 |
| T-EDIT-8 | T-ADD-3의 사본 7개 | 11-30 사본의 날짜를 12-01, 제목을 "대학수학 보강"으로, `THIS_AND_AFTER` | 그 사본만 12-01로 옮겨 간다. 그 사본과 12-07부터 12-28까지 제목이 "대학수학 보강". 11-16, 11-23은 그대로 |

## 5. `void TaskBook.delete(Task task, DeleteScope scope)`

일정을 지운다.

- **쓰는 곳**: UC-06
- **입력**: 지울 일정, 범위(`ONLY_THIS` 또는 `THIS_AND_AFTER`). 반복 사본이 아니면 화면은 범위를 묻지 않고 `ONLY_THIS`를 넘긴다.
- **하는 일**: `THIS_AND_AFTER`는 같은 `seriesId`에서 날짜가 같거나 뒤인 사본을 모두 지운다. 끝낸 할 일을 지워도 보유 포인트, 경험치, 오늘 상한 횟수는 그대로다(D-19). 보상을 받았던 일정은 `deletedRewarded`에 남겨, 친밀도(27번)와 통계 포인트(29번)가 지워도 줄지 않게 한다(`rewardHistory`는 남은 일정과 이것을 합친다).

| 검사 | 처음 상태 | 하는 것 | 결과 |
|---|---|---|---|
| T-DEL-1 | 오늘 끝내 10P를 받은 할 일, 보유 30P, 오늘 횟수 1 | 지움 | 일정이 없어진다. 30P, 경험치, 횟수 1 그대로 |
| T-DEL-2 | T-ADD-3의 사본 7개 | 12-07 사본을 `ONLY_THIS` | 6개 남음 |
| T-DEL-3 | T-ADD-3의 사본 7개 | 12-07 사본을 `THIS_AND_AFTER` | 11-16, 11-23, 11-30만 남음 |

## 6. `DayPlan TaskBook.dayPlan(LocalDate date)`

메인 할 일 목록에 보일 하루 시간표를 만든다(D-31).

- **쓰는 곳**: UC-01, UC-09 (메인 할 일 목록)
- **입력**: 고른 날짜
- **출력**: 두 묶음. `timed`는 그 날짜의 시작 시각이 있는 할 일과 고정 일정이고 시작 시각 순, 같으면 `seq` 순이다. `untimed`는 그 날짜의 시작 시각이 없는 할 일이고 `seq` 순이다. 끝낸 할 일도 제자리에 있다. 줄마다 보일 시각 글자는 `timeText(Task)`가 "시작~끝"으로 만들고, 끝이 자정이면 "24:00"으로 쓴다.
- 브리핑의 남은 수(16번 1번 문장)와 성취도 막대(13번)는 그 날짜의 할 일과 고정 일정을 모두 센다(D-35). 달력 칸 제목(26번)은 할 일(`TASK`)만 본다.

## 16. `String PetTalk.say(Situation situation, ...)`

펫 말풍선의 문장을 만든다. 말풍선은 다음 말이 올 때까지 남아 있다.

- **쓰는 곳**: 메인, 일정관리, 나의 방의 말풍선. 말하는 펫은 고른 펫이다(D-48)
- **하는 일**: 아래 표의 문장을 그대로 쓴다. `{}`는 값으로 바꾼다. 제목이 15자를 넘으면 앞 14자 뒤에 "…"를 붙인다. 이름 뒤의 "이야/야"는 이름 마지막 글자가 받침 있는 한글이면 "이야", 그 밖이면 "야"다.
- `BRIEFING`은 아래 문장들을 이 순서로 띄어 쓰고, 해당하지 않는 문장은 뺀다.
  1. 셀 때 고정 일정도 넣는다(D-35). 오늘 할 일이 없으면 "오늘은 할 일이 없어.", 남은 것이 있으면 "오늘 할 일 {남은 수}개 남았어.", 다 끝냈으면 "오늘 할 일은 다 끝냈어!"
  2. 어제 날짜의 끝내지 않은 할 일이 있으면 "어제 못 끝낸 일 {수}개는 달력에 남아 있어."
  3. 내일부터 사흘 안 날짜의 끝내지 않은 할 일 가운데 날짜, `seq` 순으로 첫 번째가 있으면 "'{제목}' 마감이 {내일이야, 모레야, 사흘 뒤야}."
  4. 1이 "할 일이 없어"이고 3이 없으면 "아래 칸에 하나 적어 볼까?"를 붙인다.

| 상황 | 언제 | 문장 |
|---|---|---|
| `FIRST_RUN` | 첫 실행의 첫 브리핑 | "안녕, 나는 {이름}{이야/야}. 일정관리에서 이번 학기 수업부터 넣어 볼까?" |
| `WELCOME_BACK` | 8일 이상 만에 브리핑 | "오랜만이야! 다시 와서 반가워." 오늘 할 일이 있으면 " 오늘 할 일은 {수}개야."를 붙인다 |
| `USUAL` | 그날 두 번째부터 창을 열 때, 메인에서 오늘을 다시 고를 때 | `BRIEFING`의 1번 문장 |

## 20. `BuyResult Shop.buy(ItemId item)`, `void Room.toggle(ItemId item)`, `int Shop.satisfaction(Set<ItemId> placed)`, `List<Item> Shop.find(String category, String query, boolean ownedOnly)`

아이템을 찾고, 사고, 방에 놓거나 치우고, 방 꾸미기 만족도를 구한다.

- **쓰는 곳**: UC-14(머리 카드), UC-15, UC-16 (나의 방 상점 칸과 미리보기 칸)
- **출력**: `buy`는 `BOUGHT`, `NOT_ENOUGH`(모자란 포인트와 함께), `ALREADY_OWNED` 중 하나. `satisfaction`은 0부터 100. `find`는 맞는 아이템을 가격 순으로
- **오류**: `toggle`에 사지 않은 아이템이면 `IllegalStateException`
- **하는 일**:
  - 아이템, 가격, 분류는 D-52의 열세 개이고(합 2210P) 상점 칸은 가격 순이다.
  - `buy`는 보유 포인트가 가격 이상이면 가격을 빼고 `ownedItems`와 `placedItems`에 넣는다(D-28). 모자라면 미리보기 칸의 구매하기가 흐리고 그 아래에 "{모자란 포인트}P 모자라요"를 보인다(D-53).

  - `satisfaction`은 놓인 아이템 가격 합을 모든 아이템 가격 합(2210)으로 나눈 백분율을 반올림한다(D-52). 배치 아이템은 "{놓인 수} / 13"이다.

## 21. `LoadResult DataStore.load()`, `void DataStore.save(AppData data)`

데이터 파일을 읽고 쓴다.

- **쓰는 곳**: UC-01, 그리고 22번 함수를 거치는 모든 변경
- **입력**: 데이터 폴더. Windows는 `%APPDATA%\PlanningPet`, macOS는 `~/Library/Application Support/PlanningPet`, 그 밖은 `~/.planningpet`이다. 파일 이름, 형식, 버전 번호와 변환 규칙은 07에서 정한다.
- **출력**: `load`는 읽은 데이터, `FIRST_RUN`(파일 없음), `UNREADABLE`(이유와 함께) 중 하나
- **오류**: `save`는 쓰지 못하면 `IOException`
- **하는 일**: `save`는 같은 폴더의 임시 파일에 쓰고 fsync한 뒤 원래 파일 자리로 옮긴다(D-08). `load`는 원래 파일만 읽고 남은 임시 파일은 지운다. `UNREADABLE`이면 앱은 파일을 건드리지 않고 이유를 보인 뒤 끝낸다(UC-01 2b).

## 22. `void AppController.change(String what, Runnable edit)`

사용자의 변경 하나를 적용하고 저장한다. 저장에 실패하면 되돌린다.

- **쓰는 곳**: 데이터를 바꾸는 모든 유스케이스(UC-02~UC-08, UC-11, UC-15~UC-17, UC-20~UC-23)
- **입력**: 저장 실패 창에 보일 이름(예: "할 일 완료"), 변경
- **하는 일**: 데이터의 복사본을 떠 두고 변경을 적용한 뒤 21번 `save`를 한 번 부른다. 실패하면 복사본으로 되돌리고 오류 창(제목 "저장하지 못했어요", 내용 "{what} 저장에 실패해서 바꾸기 전으로 돌렸어요.")을 띄운다. 일정 입력 창은 이때 닫지 않고 입력값을 남긴다. 저장에 성공하든 되돌리든 마지막에 데이터 변경 알림을 한 번 보낸다. 데이터를 보이는 모든 부품(위 막대, 달력, 할 일 목록, 성취도 막대와 그 위의 펫, 레벨 막대, 시간표, 일정관리 오른쪽 목록, 일정관리의 펫, 나의 방의 머리 카드와 방과 펫 패널과 상점 칸, 캐릭터, 통계)은 이 알림을 받아 다시 그린다. 알림을 받지 않는 부품이 있으면 그 부품만 옛 값으로 남는다.

| 검사 | 처음 상태 | 하는 것 | 결과 |
|---|---|---|---|
| T-SAVE-1 | 늘 실패하는 저장소, 30P | 할 일 완료 | 할 일 `done` false, 30P, 경험치와 횟수 그대로. 내용 "할 일 완료 저장에 실패해서 바꾸기 전으로 돌렸어요." |
| T-SAVE-2 | 같음, 120P | 쿠션 사기 | 120P, 쿠션 없음 |
| T-SAVE-3 | 같음 | 일정 입력 창에서 저장 | 일정 그대로, `nextSeq` 그대로, 창이 열린 채 입력값 그대로 |
| T-SAVE-4 | 정상 저장소 | 할 일 완료 | 저장 1번 |
| T-SAVE-5 | 정상 저장소, 메인 화면, 오늘 할 일 4개 중 1개 끝냄 | 할 일 하나 완료 | 알림 1번. 그 알림에서 보유 포인트, 목록의 체크, 성취도 막대 위 펫의 자리(2/4), 레벨 막대가 함께 바뀐다 |

## 23. `void DayWatcher.tick(LocalDateTime now)`

켜 둔 채 앱 날짜가 바뀌면 화면을 새 날에 맞춘다.

- **쓰는 곳**: 17번과 같은 30초 타이머
- **하는 일**: 마지막 확인 때의 앱 날짜와 지금의 앱 날짜가 다르면 한 번 알린다. 그러면 달력의 오늘 표시, 출석 버튼, 성취도 막대를 새 날로 다시 그린다. 메인에서 고른 날짜가 옛 오늘이었으면 새 오늘로 옮기고, 다른 날을 보고 있었으면 그대로 둔다. 창이 보이는 중이면 15번 `onWindowShown`을 부른다(D-23).

| 검사 | 처음 상태 | 하는 것 | 결과 |
|---|---|---|---|
| T-DAYW-1 | 마지막 확인 11-17 03:59:40 | 04:00:10에 확인, 이어서 04:00:40에 확인 | 처음에 11-17로 바뀜을 한 번 알림. 다음에는 없음 |
| T-DAYW-2 | 창이 보임, `lastOpenDay` 11-16 | 11-17로 바뀜 | `BRIEFING`, 연속 접속 하나 늘어남 |
| T-DAYW-3 | 창이 숨겨짐 | 11-17로 바뀜 | 말 없음. 나중에 창을 열 때 `BRIEFING` |
| T-DAYW-4 | 고른 날짜 11-16 | 11-17로 바뀜 | 고른 날짜 11-17. 고른 날짜가 11-20이었으면 11-20 그대로 |
| T-DAYW-5 | 마지막 확인 11-16 23:00, 잠자기 | 11-18 10:00에 깨어나 확인 | 11-18로 바뀜을 한 번만 알림 |

## 24. `boolean SingleInstance.acquire()`

앱이 하나만 실행되게 한다.

- **쓰는 곳**: UC-01 1a. `main`이 데이터를 읽기 전에 부른다.
- **출력**: 이 프로세스가 첫 실행이면 true. 이미 실행 중인 앱이 있으면 그 앱에 창을 보이라고 알리고 false.
- **하는 일**: 데이터 폴더의 잠금 파일을 운영체제 파일 잠금으로 잡는다. 잡은 프로세스는 `127.0.0.1`의 빈 포트에서 신호를 기다리고 그 포트 번호를 잠금 파일에 적는다. 못 잡은 프로세스는 그 포트로 신호를 보내고 끝난다. 프로세스가 죽으면 운영체제가 잠금을 풀어 준다.

| 검사 | 처음 상태 | 하는 것 | 결과 |
|---|---|---|---|
| T-ONE-1 | 실행 중인 앱 없음 | 실행 | true |
| T-ONE-2 | 앱 A 실행 중, 창 숨김 | 앱 B 실행 | B는 false로 끝나고 A의 창이 보이며 15번이 불린다 |
| T-ONE-3 | 앱 A를 `kill -9`로 끝냄 | 앱 B 실행 | true |

## 25. 창 닫기, 끝내기, 컴퓨터 켤 때 실행

`planningpet.app`의 `AppController`와 창 틀이 함께 맡는다.

- **쓰는 곳**: UC-18, UC-19
- **하는 일**:
  - 창의 닫기 버튼은 창을 숨긴다. `trayNoticeShown`이 false면 운영체제 알림 "플래닝펫은 트레이에서 계속 알림을 보내요"를 띄우고 true로 저장한다.
  - 트레이 아이콘을 누르면 메뉴(열기, 끝내기)가 뜬다. 열기는 창을 보이고 15번을 부른다.
  - 트레이 메뉴의 끝내기와 macOS의 Cmd+Q는 앱을 끝낸다. `SystemTray.isSupported()`가 false면 창의 닫기 버튼도 앱을 끝낸다(D-29).
  - 컴퓨터 켤 때 실행을 켜면 Windows는 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`에, macOS는 `~/Library/LaunchAgents/com.planningpet.app.plist`(`RunAtLoad` true)에 설치된 앱의 경로와 `--autostart`를 등록한다. 끄면 지운다. 설정 화면을 열 때마다 등록 상태를 운영체제에서 다시 읽어 체크박스에 보인다.
  - 실행 JAR로 켰으면 체크박스가 비활성이고 그 아래에 "설치 파일로 설치했을 때만 쓸 수 있어요"를 보인다.

| 검사 | 처음 상태 | 하는 것 | 결과 |
|---|---|---|---|
| T-WIN-1 | `trayNoticeShown` false | 창 닫기 | 창 숨김, 앱 실행 중, 안내 알림, `trayNoticeShown` true로 저장 |
| T-WIN-2 | `trayNoticeShown` true | 창 닫기 | 창 숨김, 알림 없음 |
| T-WIN-3 | 트레이 미지원 | 창 닫기 | 앱이 끝남 |
| T-WIN-4 | 설치된 앱, 실행 등록 없음 | 체크 켬 | 운영체제에 등록됨. 다시 설정을 열면 체크된 채로 보임 |
| T-WIN-5 | T-WIN-4 뒤 운영체제 설정에서 등록을 지움 | 설정을 엶 | 체크 꺼진 채로 보임 |
| T-WIN-6 | 실행 JAR | 설정을 엶 | 체크박스 비활성, 안내 문장 보임 |
